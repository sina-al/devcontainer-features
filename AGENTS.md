# AGENTS.md

Guidance for AI agents working in this repository. It is the durable, machine-readable
complement to `README.md`; if they disagree, README is the user-facing truth and this
file should be updated to match.

## What this repo is

`sina-al/devcontainer-features` is a **public, canonical collection of self-authored
dev container features**. Owning the features I depend on removes the trust gap with
third-party features: I control the install code, versions, tests, and published
artifacts. Features publish to GHCR as
`ghcr.io/sina-al/devcontainer-features/<feature>:<version>` and are referenced by major
version (for example `ghcr.io/sina-al/devcontainer-features/fireconnect:1`).

The structure and publish workflow are derived from the official template
`devcontainers/feature-starter` (formerly `feature-template`). Do not hand-roll the
layout or the release workflow — derive them from the template and the
[Feature distribution spec](https://containers.dev/implementors/features-distribution/).

## Conventions (bake into every feature)

- **Install as the remote user** via `su - "${_REMOTE_USER:-${_CONTAINER_USER:-vscode}}"`,
  so launchers, `~/.local/bin`, and `PATH` updates land in the user's home, not `/root`.
  A feature runs as root at build time; running the vendor installer as-is would put the
  tool in `/root` and off the sandbox user's `PATH`.
- **Pin everything.** Each feature exposes a `version` option for the tool; the feature's
  own `version` in `devcontainer-feature.json` is semver; consumers reference `:1` (major).
  No floating tags in published references.
- **No secrets in features.** Auth/login is a runtime step (for example `fireconnect
  login`), not build-time, unless there is an explicit opt-in (`login: true` + token env)
  for CI. Even then, prefer `login: false` (the default) — `login: true` bakes the token
  into the image layer and the feature output.
- **Tests are required.** Every feature has `test/<feature>/scenarios.json` + `test.sh`.
  Scenarios that need a dependency (for example fireconnect needs `node`) include that
  feature explicitly in `scenarios.json`; `installsAfter` is an ordering hint, not a
  declaration that pulls a dependency into the test image. Dependency-free features also
  get an auto-generated test (`--skip-scenarios`); dependency-needing ones run via
  scenarios only (`--skip-autogenerated`).
- **Mirror the template.** Use `dev-container-features-test-lib` (`check`, `reportResults`)
  in test scripts. Keep `release.yaml` and `validate.yml` as the template ships.

## Security posture

- **Never bake secrets into the repo, image, or feature output.** No API keys, tokens, or
  credentials. This is a hard rule.
- **Treat agents as compromised processes** when handling secrets: anything readable by
  the container's user is readable by the agent.
- **`login: true` is the only build-time auth path** and it is documented as baking the
  token into the image layer. Prefer it only for reproducible CI, never personal sandboxes.

## Gotcha: relative feature paths

Relative feature paths in a consumer's `devcontainer.json` resolve relative to the
**`.devcontainer/` folder**, not the repo root. It does not affect this repo's own
devcontainer (features here live in `src/` and are referenced by id after publish), but it
bites any local-feature references in consumer repos.

## Work on this repo

This repo has its own devcontainer (`.devcontainer/`) intended to be run with
[DevPod](https://devpod.sh). It provides Docker-in-Docker and the `devcontainer` CLI so
`devcontainer features test` works inside it. See README §Work on this repo.
